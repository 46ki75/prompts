## What RFC 7231 defines as the semantics of PUT

RFC 7231 ("Hypertext Transfer Protocol (HTTP/1.1): Semantics and Content," June 2014) defines PUT in Section 4.3.4. The core semantics it specifies are:

1. **Replacement of state at the target resource.** A PUT request asks that the state of the target resource be created or replaced with the state defined by the representation enclosed in the request message payload. The server is being told, "make the resource at this URI have this representation."

2. **Create-or-replace behavior.**
   - If the target resource does not exist and the PUT successfully creates it, the origin server MUST send a `201 (Created)` response.
   - If the target resource does exist and is successfully modified to reflect the enclosed representation, the origin server sends either `200 (OK)` or `204 (No Content)` to indicate successful completion.

3. **Idempotent, but not safe.** PUT is defined as idempotent: the intended effect on the server of multiple identical PUT requests is the same as for a single such request. It is not "safe" because it does modify resource state.

4. **Distinction from POST.** The fundamental difference between POST and PUT is reflected in the request URI. With PUT, the enclosed representation is the desired state for the URI in the request line; with POST, the URI identifies a resource that will *process* the representation. Consequently, PUT to a collection-style URI does not mean "append a new member" — it means "replace the collection's representation."

5. **Server discretion over the representation.** The server is not required to store the representation byte-for-byte. It may transform, validate, or reject the representation. If the server applies transformations such that a subsequent GET would return something materially different from what was PUT, the server SHOULD send a `200 (OK)` response containing a representation describing the result, and it ought to inform the user agent (e.g., via response headers) of the divergence. The server MAY reject a PUT whose representation it considers inconsistent with the resource's constraints, typically with `409 (Conflict)` or `415 (Unsupported Media Type)`.

6. **Interaction with caches and validators.** A successful PUT invalidates stored cache responses for the effective request URI. RFC 7231 also notes that PUT requests can carry conditional headers (e.g., `If-Match`, `If-Unmodified-Since`) to avoid the "lost update" problem when multiple clients are writing concurrently.

7. **Content-Range with PUT is discouraged.** RFC 7231 (and the related range spec) note that a PUT request with a `Content-Range` header is not defined by the standard semantics and SHOULD be rejected; partial updates are the province of PATCH (defined separately in RFC 5789), not PUT.

8. **No defined request body semantics for safe interpretation.** Unlike GET or HEAD, PUT has no defined cacheable response semantics in the general case; responses to PUT are not cacheable unless explicit cache-control information makes them so.
